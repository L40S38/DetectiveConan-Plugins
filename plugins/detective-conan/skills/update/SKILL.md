# 名探偵コナン データ更新

`data/` 以下のデータを、`data/conventions.md` の約束事を守って書き換える。最後に `lint_data.py` と markdownlint を通し、何を変えたかを表で示す。

## Step 0: 編集する場所を確かめる

- 編集するのは **ソースリポジトリ**（DetectiveConan-Plugins）で、インストール済みプラグインのキャッシュ（`~/.claude/plugins/cache/...`）ではない。キャッシュを直しても、次の更新で消える。
- カレントディレクトリに `.claude-plugin/marketplace.json` があり、`"name": "detective-conan-plugins"` になっているか確かめる。無ければ、ソースリポジトリのパスをユーザーに聞く。
- 以降のパスは、ソースリポジトリの `plugins/detective-conan/` からの相対パスで書く。

## Step 1: 何を反映するかを決め、情報を集める

1. 反映する範囲をユーザーと確かめる（例：「File 1168」「109巻」「劇場版第 30 作」「表3 の世良」）。
2. 単行本が出たときは、database を最新にする。

   ```sh
   cd plugins/detective-conan/database
   python ConanData.py
   python PatchData.py
   python Case.py && python FileTitle.py && python GuestCharacter.py && python MainCharacter.py && python Place.py
   cd ..
   python scripts/conan_db.py latest
   python scripts/conan_db.py anomalies
   ```

   `PatchData.py` は、編纂室のページそのものの誤り（事件の境目の誤りなど）を、`database/patches.json` に従って直す。`ConanData.py` で取り直すと、直した誤りも編纂室のとおりに戻るので、必ず CSV を作る前に実行する。「直す対象が無い」と出たパッチは、編纂室側で直ったかを確かめ、直っていれば `patches.json` から消す。
   `anomalies` で新しい欠け・重複が出たら、報告に含める。原作で確かめて編纂室の誤りだとわかったら、`patches.json` に足して `PatchData.py` からやり直す。submodule に差分が出たら、コミットと push が必要なことをユーザーに伝える（勝手に push しない）。
   database を更新したら、`単行本未収録` の形で書いていた File（`grep -rn 単行本未収録 data/`）のうち、`conan_db.py file` で引けるようになったものを、`conventions.md` の 3.1「database に入っている話」の形に直す。出来事の正本の `data/events/01-manga/unpublished.md` のグループは、事件の形の見出しに直して、巻のファイルへ移す（件の ID は変えない）。
   database の更新で、事件名や話タイトルが変わることがある（単行本の収録時に改題されるなど）。更新の前後で `database/dataset_csv/Volume-Index-Case-Title.csv` を見比べ（submodule の中で `git diff` する）、名前が変わった事件・話があったら、`data/` 以下で古い名前を使っている箇所（`grep -rn "古い名前" data/`）をすべて新しい名前に直す。直した事件名は Step 9 の報告に含める。`lint_data.py` は File 表記の形しか見ず、名前が database と合っているかは見ないので、この確認は省かない。
3. `data/sources.md` の信頼度の順に情報を集める。単行本未収録の話は、D の速報系 2 サイト以上で一致したものだけを使う。WebFetch の要約は細部を取り違えることがあるので、話数と人物名は原文か database で確かめる。

## Step 2: 出来事の正本（data/events/）

出来事の正本は、作中の場面に ID を振ってまとめたもので、知識表・人物の掘り下げの脚注、relationships の経緯、伏線などの根拠になる。1 件の欄、「出来事」の書き方（知識・関係・伏線・描写・生死のラベル）、ID の振り方と略号の表は `data/events/README.md` と `conventions.md` の 11. にある。

### 確かめ方（必ず守る）

正本はほかのファイルの根拠になるので、1 件でも間違いが入るとあちこちに広がる。記憶や推測では書かず、次の手順で少しずつ書く。

1. **書き写しから始める。** 出来事の中身は、今のデータ（知識表・人物の掘り下げの脚注、relationships の経緯、`profiles/timeline.md`）にある文をそのままコピーしてから整える。自分の記憶や Web の要約をもとに新しく書かない。
2. **写し元を記録する。** 各件の「写し元」に、どのファイルのどの脚注・項目から写したかを書く（脚注 ID や見出しで書く。行番号は変わるので使わない）。
3. **写したことを機械的に確かめる。** 写した文が写し元にそのまま含まれているかを、grep かスクリプトで確かめる。今のデータ（`data/` 以下）や database のあらすじから写した件は、`python scripts/check_event_copy.py <ID>` で確かめられる。整えたときに言い換えた部分は、写し元とどこが違うかを示す。
4. **話数を引き直す。** File 番号・話タイトル・事件名・巻は、写し元をそのまま信じず、`conan_db.py` で引き直す。写し元のほうが間違っていたら、正本には正しい値を書き、写し元の誤りは一覧にしてユーザーに伝える（写し元は、正本の作業とは別に直す）。
5. **写し元に無いことを足さない。** その場にいた人物、台詞の文言、作中の時期などを推測で埋めない。原作・database・日本語の出典で確かめられたものだけを、出典を付けて足す。確かめられなければ「要確認」と書くか、空けておく。とくに「場面にいた人物」は、その場面に描かれているかを確かめてから入れる（その回に出ているだけでは入れない）。
6. **食い違いはまとめない。** 同じ場面について写し元どうしで書き方が食い違っていたら、どちらかに寄せない。両方を写して「要確認」にし、ユーザーに伝える。
7. **少しずつ進める。** 1 回に書くのは 1 場面（または 1 つの話）分だけにする。書くたびにユーザーに見せ、確かめてもらってから次へ進む。
8. **Agent に調べさせたとき**は、結果をそのまま正本に入れない。写し元・database・原文と突き合わせてから入れる。
9. **台詞は日本語の出典で確かめ、英語のページから訳し戻さない。** WebFetch などの要約は細部を取り違えるので、話数と人物名は原文か database で確かめる。

新しい話の場面など、今のデータに写し元が無い件は、database のあらすじ・原文・`sources.md` の D の速報系 2 サイト以上で一致したものから書き、確かめた出典を写し元の欄に書く。

### 手順

1. 件を置く場所を決める。ファイルは区分で決まる（`data/events/README.md` の「ファイル」）。原作のグループは database の事件で、`python scripts/conan_db.py file <番号>` と `python scripts/conan_db.py case <事件名>` で事件と File の範囲・巻を引き、事件の最初の巻のファイル（例：104巻なら `data/events/01-manga/104.md`）に書く。database に無い話は `data/events/01-manga/unpublished.md` に書く。ファイルやグループが無ければ、話の順の位置に作る。
2. 写し元の文を写して件を書く。ID は、グループの中で次の番号（2 桁）にする。
   - 今のデータから写したときは、写し元の欄に、作業しているブランチを作った main のコミット（`git rev-parse --short $(git merge-base HEAD origin/main)`）と、脚注 ID・見出しを書く。`check_event_copy.py` はコミットの時点の中身を読むので、main に入っている文から写す（同じブランチで直した文は写さない）。
   - 前の PR で作った件に、別のファイルから写した文を足すときは、前の写し元の行は変えずに、そのときのコミットで写し元の行を 1 行足す（`data/events/README.md` の「写し元の書き方」）。
   - ラベル（知識・関係・伏線・描写・生死）の下には、写し元がその出来事を根拠にしていると書いているものだけを書く。
3. 写しを確かめる。今のデータや database のあらすじから写した件は `python scripts/check_event_copy.py <ID>` を使い、「違いあり」の文は、整えた部分として違いをユーザーに見せる。ラベルの下の K・P・F の ID が写し元に出てこなければ直す。新しい話の件など、Web の出典から書いた件はスクリプトでは確かめられないので、出典と 1 文ずつ見比べて示す。
4. 話数を引き直して見つかった写し元の誤りと、写し元どうしの食い違いを一覧にする。
5. Step 8 のチェックを通し、1 件（1 場面）ごとにユーザーに見せて、確かめてもらってから次の件へ進む。

ほかのファイル（Step 3〜6）で場面を根拠に書くときは、その場面の件があれば ID で参照できる（例：「K4-2 は E-1106-01 による。」）。参照した ID が実在するかは `lint_data.py` が見る。

今の File 表記の根拠を ID に置き換えるときは、`data/events/README.md` の「根拠を ID に置き換えるとき」に従う。置き換えたら、`python scripts/check_event_copy.py --removed <ブランチを作った main のコミット> <data からのパス>` で、消した文が件に写されているか（または脚注に残っているか）を確かめ、「違いあり」「見つからない」の文をユーザーに見せる。

## Step 3: 伏線リスト（data/foreshadowing/）

`data/foreshadowing/README.md` が一覧表、分類ごとの詳細は `data/foreshadowing/01-org.md`〜`09-rel.md`（分類と番号の対応は README.md の「ファイル一覧」を見る）。

- 新しい謎を見つけたら、分類ごとに次の番号で項目を立てる。ID は再利用しない。
- **タイトルは謎の形**で書き、答えも、ほかの謎の答えになる名前も入れない（`conventions.md` の 5.）。
- `README.md` の一覧表と、対応する分類ファイルの詳細の両方に書く（ID・タイトル・状態・重要度・初出・回収）。
  - 詳細の項目には、見出しの前に `<a id="F-XXX-NNN"></a>` を置く。アンカー・見出し・箇条書きのあいだは空行を 1 行ずつあける（既存項目にならう。空行が無いと markdownlint のエラーになる）。README.md の一覧表からはこのアンカーへリンクする（`ファイル名#F-XXX-NNN`）。
  - 「関連」欄で人物・知識表に触れるときは、`characters.md#C-xxx`／`../knowledge-matrix/0N-〜.md` へのリンクにする（既存項目の書き方にならう）。
- 回収されたら「状態」を変え、「回収」欄に話数と答えを書く。答えを書くのは「回収」欄だけ。
- 途中の進展は「経過」欄に時系列で足す。

## Step 4: 考察項目リスト（data/open-questions.md）

- 新しい事実を「確定している事実」に話数つきで足す。新しい説には `[ファン説]` を付け、根拠と反証を書く。
- 解明された項目は消さずに、末尾の「解明済み」セクションへ移し、どの話で解明されたかを書く。
- 新しい大きな問いが生まれたら、次の番号で項目を立てる（タイトルの書き方は伏線と同じ）。

## Step 5: 人物索引（data/characters.md）

- 新しい人物はカードを足し、別名があれば「(a) 別名 → 人物 ID」にも足す。初登場は `python scripts/conan_db.py char <名前>` で引く。原作より先に劇場版・アニメなどで出ていたら「／先行：」を付ける。
- database で肩書・偽名・変装時の呼び名など、カードと違う名前で載っている人物は、その呼び名を「(a) 別名 → 人物 ID」に種別「database の呼び名」で足す（例：「大滝警部」）。`conan_db.py char` は、カードの見出しと別名表にある同じ人物の名前でも引く。同じ人物が事件によって違う呼び名で載っているときは、Step 1 の `patches.json` で編纂室がほかの事件で使っている名前にそろえる（`rename_guest`）。
- 所属・生死・役割が変わったら書き換え、根拠の話数を付ける。
- 新しい劇場版が公開されたら、「(c) 劇場版への登場」に行を足す。
- 人物やグループ（`###`）を足したとき、人物を別のグループへ移したときは、Step 6 で知識表と人物の掘り下げにも反映する。

## Step 6: 知識表と人物の掘り下げ（data/knowledge-matrix/・data/profiles/）

記号と「コナンの把握」の列の意味、行の選び方（グループ分け・並び順・個別の行とまとめ行の基準と書式）は `data/knowledge-matrix/README.md` に書いてある。行の置き方はこの README に従う。

- 値が変わったセルを直し、脚注に根拠の話数を書く。`?` のセルを確かめられたら、記号に置き換えて根拠を書く。
- 値が変わって、個別の行とまとめ行のどちらに入るかが変わったら、行を移す（位置と書式は README の「行の選び方」）。
  - まとめ行（`ほかの「<グループ名>」：…` の行）の人物に、「コナンの把握」以外で `✕` 以外の値（`?`・`✕†` を含む）が付いたら、まとめ行から名前と ID を消して個別の行を作る。まとめ行に誰も残らなくなったら、まとめ行ごと消す。
  - 個別の行が「コナンの把握」以外すべて `✕`（`†` なし）になったら、その行を消してまとめ行に名前と ID を入れ、ほかの行で使っていない脚注も消す。まとめ行が無ければ作る。
- Step 5 で人物を足したら、すべての表（`data/knowledge-matrix/0*.md`）にその人物を入れる。確かめていない人物の扱い（その表の情報に触れる機会が無ければまとめ行、知っていてもおかしくなければ `?` の個別の行）も README の「行の選び方」に書いてある。
- Step 5 でグループを足したら、すべての表に見出し行を足す。人物を別のグループへ移したら、すべての表で、その人物の行（またはまとめ行の名前）を新しいグループへ移す。
- `data/knowledge-matrix/README.md` と `conventions.md` の「情報時点」を更新する。
- 足し忘れ・重複・並び順・グループの食い違いは、Step 8 の `lint_data.py` がエラーにする。
- 人物の掘り下げ（`data/profiles/0*.md`）も、行の置き方は知識表と同じ（記号も同じ。「コナンの把握」の列は無く、まとめ行に入れるのは、すべての列が `✕` の人物）。人物やグループを足したら、こちらの表にも入れる。値と過去の区分は `data/profiles/README.md` を見る。

## Step 7: 参考サイト（data/sources.md）

新しく使ったサイトは、URL が開けることを確かめてから、信頼度を付けて足す。「最終確認日」を更新する。

## Step 8: チェックする

```sh
npm run fix:md    # Markdown の書式を自動で直す（初回だけ先に npm ci）
python scripts/lint_data.py
npm run lint:md
```

fix:md は data/ のファイルも書き換えるので、lint_data.py はその後に実行する。lint_data.py と lint:md のどちらもエラーが 0 件になるまで直す。lint_data.py の警告（タイトルの書き方）は、答えが入っていないことを目で確かめる。markdownlint の設定はリポジトリ直下の `.markdownlint-cli2.jsonc` にある（`data/foreshadowing/`・`data/relationships/` には、そのディレクトリだけの例外を書いた同名のファイルがある）。

## Step 9: 変更をまとめて示す

```markdown
# データ更新：File 1168 まで

| ファイル | ID・場所 | 変更 | 根拠 |
|---|---|---|---|
| foreshadowing/02-rum.md | F-RUM-009 | 経過を追加 | 原作 File 1168 [原作] |
| knowledge-matrix/03-akai-family.md | 世良真純 K3-2 | △ → ◎ | 原作 File 1168 |
| events/01-manga/unpublished.md | E-1168-01 | 追加（写し元：D の速報系 2 サイト） | 原作 File 1168 [原作] |

- lint：lint_data.py エラー 0 件・警告 0 件／markdownlint エラー 0 件
- 要確認のまま残したもの：…
- database：更新あり／なし（submodule のコミットと push が必要）
- database で名前が変わった事件・話：なし／「旧名」→「新名」（data/ の該当箇所を直した）
```

コミットはユーザーから頼まれたときだけ行う。
